## 四、实现方法

### 4.1 sys_trace

根据 trace_request 处理三类请求：

- 请求 0：把 id 作为地址，读取该地址的一个字节并返回。
- 请求 1：把 data 的低 8 位写入 id 指定的地址，返回 0。
- 请求 2：把 id 作为系统调用编号，返回当前任务对该系统调用的调用次数。
- 其他请求：返回 -1。

### 4.2 系统调用次数统计

在 syscall 分发函数进入 match 前调用 record_syscall。
因此，每次系统调用都会先被统计，再执行具体处理函数。
查询 sys_trace 自身的次数时，本次查询也已经计入。

计数表使用二维数组，通过“任务编号”和“系统调用编号”索引。
不同任务使用不同的行，避免把所有任务的次数累加在一起。
查询超出计数表范围的编号时返回 -1。

### 4.3 计数表的存储方式

最终将计数数据放在独立的静态变量 SYSCALL_COUNTS 中，
通过 UPSafeCell 获取可变访问权限。

为支持直接静态初始化，将 UPSafeCell::new 修改为 const unsafe fn。
同时从 TaskControlBlock 及其局部初始化表达式中移除计数数组，
避免初始化任务管理器时在启动栈上创建过大的临时数据。

该方案沿用当前框架的单核使用约束，不将 UPSafeCell 视为多核锁。

## 五、问题与排查

### 5.1 现象

完整本地评测最初只有 1/7 通过。
ch3_sleep 读取到时间为 0，触发 current_time > 0 断言失败；
其他依赖时间推进的测试无法完成，最终出现 QEMU 超时。

### 5.2 原因

最初在每个 TaskControlBlock 中加入了 [usize; 512]。
在 64 位目标上，每个计数数组占 4096 字节。
16 个任务的计数数组合计占 65536 字节，
加上任务状态和任务上下文后，超过了 64 KiB 启动栈的容量。

反汇编显示，相关初始化函数的栈帧达到 67584 字节。
栈溢出覆盖了相邻数据，其中包含时间换算所需的常量，
导致时间读取异常，继而影响 sleep 和 trace 测试。

### 5.3 验证与修改

排查时在临时副本中仅把启动栈增大到 128 KiB，
同一批完整测试的输出通过了 ch3 评分脚本的 7/7 检查，
支持了启动栈溢出这一判断。

最终实现采用独立静态计数表，避免在启动栈上构造大数组。


## 六、实验收获

1. 为什么全局对象的初始化仍然可能消耗启动栈。
    全局对象的最终存储位置和它的初始化过程是两回事。

你的 TASK_MANAGER 在 [task/mod.rs (line 50)](/home/kejiawang/2026a-rcore-wmjjkk/os/src/task/mod.rs:50) 中使用 lazy_static! 定义。它不是在编译时完成所有初始化，而是在第一次使用时执行初始化代码。初始化过程中有一个局部变量：
let mut tasks = [TaskControlBlock {
    task_cx: TaskContext::zero_init(),
    task_status: TaskStatus::UnInit,
}; MAX_APP_NUM];
执行这段代码时，编译器可能先在当前栈上构造 tasks，再将结果放入全局对象。具体是否产生临时值以及占用多少空间，取决于代码和编译结果。

之前每个 TaskControlBlock 都包含 [usize; 512]，16 个任务的计数数组就占了 64 KiB，再加上任务上下文等字段，超过了原来的 64 KiB 启动栈。我们查看当时的编译结果，确认初始化函数的栈帧为 67,584 字节，发生了栈溢出。

现在代码把计数表改为普通 static 变量 SYSCALL_COUNTS，并使用 const 构造函数直接静态初始化。这样，运行时初始化 TASK_MANAGER 时就不再需要在栈上构造那张大计数表。
2. 为什么系统调用次数需要按任务分别保存。
    作业要求查询当前任务调用某个系统调用的次数，不同任务各自运行、各自发起系统调用，统计结果应互不影响。
